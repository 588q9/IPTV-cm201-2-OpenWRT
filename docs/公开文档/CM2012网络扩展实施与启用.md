# CM201-2 网络扩展实施与启用

本轮只实施 CM201-2。SFT1200 保留原评估资料，后续独立研究。设计依据为 [DDNS、异地访问与 LAN 自动分流方案](DDNS与异地访问及代理方案.md)，验证范围见本文末节。

## 功能与默认状态

| 功能 | 本机入口 | 默认状态 |
| --- | --- | --- |
| Cloudflare IPv4 DDNS | LuCI「服务 → 动态 DNS」 | 停用，记录和 Token 为空 |
| Tailscale 子网访问 | LuCI「服务 → CM201-2 异地访问」 | 停用；授权来源为空，不放行 LAN 或管理端口 |
| Mihomo LAN IPv4 自动分流 | LuCI「服务 → CM201-2 代理」 | 停用，无订阅 |
| MetaCubeXD | 代理页面显示当前 LAN HTTPS 面板入口 | 核心启用并通过检查后开放 |
| 代理健康与回滚守卫 | `cm2012-proxy-guard` | 安装后运行；停用状态不接管流量 |

保留原厂 3.18 内核、无线、LAN DHCP 和盒子系统解析。只处理从当前 LAN 入口进入的 IPv4 转发与 TCP/UDP 53；终端须以盒子为默认网关和 DNS。IPv6、应用内置 DoH/DoT 尚未覆盖。

Tailscale 固定 1.104.1，Mihomo 固定 v1.19.32，yq 固定 v4.44.3，MetaCubeXD 固定发布提交；程序、公开证书、静态面板和 APK 均进入资源锁。订阅、Token、设备密钥与生成配置只留设备本地，不进入镜像或公开清单。

## SSH 构建与增量安装

以下命令使用 Python 3.12。SSH 必须已经信任设备主机密钥，并具备 root 公钥登录；不会自动接受未知主机密钥。

```powershell
python tools/project.py prepare
python tools/project.py build --ssh-host 192.168.50.1 --output output/network
python tools/project.py verify --output output/network
python tools/project.py network-bundle --ssh-host 192.168.50.1 --rootfs output/network/rootfs.tar.gz --output output/network-update.tar.gz
python tools/project.py network-deploy --ssh-host 192.168.50.1 --bundle output/network-update.tar.gz --action check
python tools/project.py network-deploy --ssh-host 192.168.50.1 --bundle output/network-update.tar.gz --action install
```

构建仅在设备独立 RAM 目录安装签名 APK，不启动该目录中的服务。原无线包索引与新增包索引按 feed 保存；通过签名索引中的内容标识选择精确候选，专用 APK 缓存避免多快照选源冲突。仍为离线安装、校验签名、禁包脚本。大型 ARM 程序和静态面板在主机合并，节省盒子 RAM。

`network-bundle` 只读快照候选路径，绑定设备真实文件的摘要、类型和权限；现有所有 UCI 配置保持原样。安装再次核对基线、父目录和临时文件冲突，保存持久备份后逐文件原子替换，并启动守卫、重启 rpcd 注册新接口。没有串口时也不重装 userdata、不改分区、boot 或引导器。完成后重新登录 LuCI，刷新浏览器页面。

增量文件由本项目管理，版本清单为 `/usr/share/cm2012/remote-assets.json`，其中包括固定程序及 APK 的版本和摘要。增量不覆盖现场全局 APK 数据库，避免丢失用户另装包的注册信息；因此 `apk info` 不代表这些增量文件的清单。完整新 rootfs 仍含 APK 原生生成的完整包数据库。不要在该旧内核设备执行整体 `apk upgrade`。

OpenWrt 发布目录会轮换索引，同 URL 不保证永久返回同一快照。`prepare` 若发现旧快照摘要变化会拒绝，使用已有可信缓存或经摘要核对的 `--import-dir`，不能换成当前索引绕过校验。

## Cloudflare DDNS

先在 Cloudflare 建独立测试子域名的 DNS only A 记录，再在标准 DDNS 页面填该记录和区域。服务选择 `cloudflare.com-v4`，用户名为 `Bearer`，密码栏填受限 API Token；Token 只授予所需 Zone 的 Zone Read、DNS Edit。

使用 HTTPS，每 10 分钟从盒子自身检查直接出口 IPv4。域名、区域和 Token 全部填妥后，在 LuCI 启用该记录，并启用、启动标准 `ddns` 服务；也可在本地 SSH 执行 `/etc/init.d/ddns enable`、`/etc/init.d/ddns start`。先核对 API 和 DNS 的实际更新结果。CGNAT 下更新成功仍不代表公网可入站；Tailscale 不依赖该 DDNS。不要在聊天、日志或公开仓库粘贴 Token。

## Tailscale

1. 在项目「异地访问」页填写测试客户端的 Tailscale IPv4 `/32`，以及需要开放的本机 TCP 管理端口，如 `22,443,5252`。来源留空时全部拒绝，不通过公网入口开放管理。
2. 保存并启用后，SSH 执行 `/usr/libexec/cm2012-tailscale login`，在自己终端打开登录链接。登录链接不会出现在公共状态接口中。
3. 在 Tailscale 控制台批准本机实际 LAN 路由，并限制 grants。配置固定不接收异地路由、不接管系统 DNS、不提供退出节点，`netfilter-mode=off`；fw3 只为明确来源和当前 LAN 配置转发与源 NAT。
4. 手机关闭 Wi-Fi，从蜂窝网络访问 LAN 的 TCP/UDP 目标。页面在线或 daemon 正常不等于真实异地访问验收通过。

网络事务未确认时暂停子网服务；LAN/防火墙稳定后幂等重协调。密钥保存在 root 私有 `/etc/tailscale`，不会写入默认镜像。

## 代理、订阅与确认

本项目生成的面板策略组按用途命名：`CM2012-DNS` 仅选择主 DoH 查询的代理出口；`CM2012-DEFAULT` 仅在订阅缺少兜底规则或明确引用本地兜底出口时生成，用于普通流量的默认分流。两者均为手动选择，订阅自带策略组保留原名和规则。旧内部名称 `CM2012-PROXY` 的规则/组引用在导入时归一为 `CM2012-DEFAULT`，新生成配置不再显示旧组名；它不是 SOCKS5 端口的专属策略组。

2026-10-25 已将命名修正同步到正在运行的盒子。名称来源是本项目 `cm2012-proxy-lib.uc` 的配置生成代码，不是订阅提供者或 Mihomo 的约定；原实现把 DoH 与缺省兜底出口合并在同一手工组，现已分开。设备当前订阅自带兜底规则，因此只显示 `CM2012-DNS`。原 DNS 选点和其他手工组选择保持一致，核心通过本地 API 热加载，Mihomo PID、revision 12、网络/DHCP/防火墙配置及策略路由基线保持不变。持久备份位于 `/etc/cm2012-proxy-group-name-f69ffc5fa020`。

本次公开回归 134 项成功（2 项 Windows 跳过），实机 ucode 纯策略/内存事务检查、真实候选 Mihomo 检查、DNS 查询及 12 个代理文件的源码摘要比对通过。首次管理请求遇到旧内核 curl 初始化取熵阻塞，原配置已恢复，后改用仅访问 loopback 的普通 HTTP 管理通路完成迁移；没有关闭 TLS 证书验证。脱敏证据在本机忽略目录 `local/audits/20261025-dns-group-rename/`。

在项目「代理」页填 HTTPS Clash/Mihomo YAML 订阅，点击「保存订阅」即可独立持久化地址，不启用代理、不需要确认。页面显示是否已保存，不回显私人地址；空订阅输入表示保留已保存地址。也可填写新地址后直接应用，新地址会先保存，启用失败或回滚均不会撤销地址保存。仅含 Base64 节点链接的订阅不能直接导入。首次启用需要当前直连出口可访问订阅服务、正确时间、当前上联 IPv4 DNS，以及至少一个被核心接受的代理节点。

选择启用并点击「应用（90 秒确认）」后，页面立即显示请求受理及下载、生成配置、核心检查、启动和分流阶段。准备阶段最多 5 分钟，不占用确认窗口；核心、TUN、本地 API、DNS 和分流规则就绪后才开始 90 秒倒计时，并允许点击「确认正常」。检查下游终端 TCP、UDP、DNS 后确认。超时、手动回滚及未确认重启恢复前一运行配置，保留已保存的订阅地址；候选失败不替换上一份有效配置。需要立即停用时点「立即恢复直连」。

下载、TLS、证书、DNS、订阅格式、地理规则、核心检查及启动故障会显示对应中文原因；不展示原始异常或包含凭据的日志。下载期间尚未启动的新核心不会被误报为失活；准备阶段仍有独立超时保护，已有运行核心的故障保护继续有效。

订阅只导入允许的节点、provider、策略组、规则和规则 provider；远端 TUN、DNS 监听、API、secret、路径和脚本不能覆盖本地设置。provider 先下载并检查，再内联交给核心。普通域名 DNS 策略经地址检查后保留，本地域名、反向解析及节点 bootstrap 有独立保护。本轮未锁定地理数据库，因此在调用核心检查前明确拒绝 GEOIP、GEOSITE、IP-ASN 等依赖地理数据库的规则，包括 classical provider 内嵌规则，保留上一份有效配置；不会隐式下载数据库。不支持的节点协议和其余配置错误由核心检查拒绝。

订阅更新由独立可取消 worker 进行，每 24 小时调度，也可手动触发。下载过程不占共用网络短锁，不阻塞 5 秒健康守卫。核心/TUN/API/DNS 连续三次故障撤销分流和 DNS DNAT，恢复新连接直连；已有 TCP 连接可能需要重连。上游代理节点断线与核心失活分别诊断。

MetaCubeXD 使用当前 LAN 地址的 HTTPS 9091/ui；本地明文 API 只在 127.0.0.1:9090。设备生成独立 secret，管理员在自己 SSH 终端读取 `/etc/cm2012-proxy/secret` 并在面板中填写。证书由设备原有 HTTPS 证书的 PEM 副本生成，不改原私钥；浏览器可能需要信任设备本地证书。

### TLS 深入诊断补充

mbedTLS 3.6.7 的实际返回码为 `-0x7280`（`MBEDTLS_ERR_SSL_CONN_EOF`），表示握手过程中底层接收已遇到 EOF。客户端日志没有收到足以定因的 TLS 错误告警；该错误本身不等同于证书验证失败，也不能确定由服务端还是中间链路关闭连接。

在同一盒子固定同一解析 IPv4、原域名 SNI 和实际 443 端口，对两个地址分别对照：curl 8.22.0 / mbedTLS 3.6.7 均为 curl 35、HTTP 000、`-0x7280`；独立 OpenSSL 3.5.9 均成功完成 TLS 1.3 握手，套件 `TLS_CHACHA20_POLY1305_SHA256`，证书和主机名验证通过、verify code 0。已排除代理环境、用户 curlrc、HTTP 重定向；curl 关闭 ALPN、固定 TLS 1.2/1.3 或指定已成功的 TLS 1.3 套件仍失败。强制 IPv4 也未改善，当前 IPv6 无连接能力。

这组初期结果一度使排查侧重握手特征兼容性或策略。后续已通过限定连接抓包、函数计时和三组安全 getrandom 单变量对照进一步定位：旧内核 `/dev/random` 取熵阻塞使 curl 的 ClientHello 延迟约 4 秒，碰上对端连接关闭；临时 getrandom 路径三次均成功并通过证书验证。详见 [TLS 握手故障诊断记录](TLS握手故障诊断记录.md)。截至 2026-10-22 尚未替换生产下载器或 TLS 库；后续正式修复见下节。上述初期脱敏证据仍保存在本机 `local/network-tls-detail-20261022.log`、`local/network-tls-pinned-20261022.log` 和 `local/network-tls-features-20261022.log`。

## 2026-10-30–31 国内视频慢速排查

针对连接 SFT1200 的终端国内视频、下载变慢，沿“终端 → SFT1200 → CM2012 → Wi-Fi 上联”检查：CM2012 到 SFT1200 约 93 Mbps，经 SFT1200 Wi-Fi 到电脑约 80–83 Mbps，短时连通性、DNS 与 CM2012 空闲资源正常；不同国内公网源约 7–38 Mbps，不能据此认定固定带宽瓶颈。明确发现终端有指向 SFT1200 的 IPv6 默认路由，但 SFT1200 的 WAN6 不可用（NO_DEVICE），两台路由器均无 IPv6 默认出口；B站、腾讯视频的 IPv4 约 13–15 ms 建连，IPv6 均在 4 秒测试限时内未成功。因此 IPv6 出口异常是视频连接等待的可能原因，尚未完成同一视频修正前后对照，不能认定为唯一根因。本轮未修改生产网络、代理或 IPv6 配置，设备临时服务和 RAM 文件已清理；2026-11-01 按使用者要求仅保留本段记录，清除本会话生成的本机诊断脚本、结果数据及临时报告，原有代码、测试与其他修改保留。
