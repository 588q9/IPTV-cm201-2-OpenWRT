# 动态节点 DNS 与浏览器恢复（2026-10-29）

用户报告桌面应用可用、浏览器网页无法访问。设备最初为 revision 20、active，TUN 与 LAN 路由存在，守卫失败计数为 0，但公共 A 查询实际超时或 SERVFAIL，11 个节点的 HTTPS 测试全部失败。电脑另有独立 Meta 虚拟接口，其本机 HTTPS 成功不能替代 CM201-2 路径验收。

## 根因与修正

10 月 28 日保存的三个节点主机地址均已变化；本轮 Cloudflare 对照答案的 TTL 只有 1 秒。昨晚固定映射能临时恢复，但不能长期适配这一订阅。本次停用该静态方案。

公开域名连通性测试发现腾讯 DNSPod 的两个 HTTPS IPv4 入口可从盒子直接访问并通过证书验证。用户明确授权：向 DNSPod 持续解析订阅节点域名，先测试，成功后应用，不发送订阅链接、密码或密钥。

隔离 RAM 核心关闭 TUN、只监听回环，去除旧节点 hosts，设置：

```json
[
  "https://1.12.12.12/dns-query",
  "https://120.53.53.53/dns-query"
]
```

结果为 11/11 节点成功，公共 DNS 恢复。生产配置只增加节点专用的实时加密解析路径；原节点 server/SNI、认证、证书验证、业务规则、策略组、TUN、系统 DNS 及普通主 DNS 路径保持。

## 实现

设备私有文件 `/etc/cm2012-proxy/node-dns.json` 保存上述数组，权限 0600。运行时读取为 `node_nameservers`，编译器校验数组上限、HTTPS、IPv4 字面量、端口及非自身地址，拒绝代理 fragment 和需要域名引导的上游。采用 IP 入口使节点解析不依赖尚未建立的代理或 DNS 服务域名的解析。

显式动态节点 DNS 生效时，生成配置仅保留原健康检查 hosts，停止使用旧节点 pins；主机地址由 Mihomo 的 DNS 解析与缓存机制更新。未设置该文件时兼容原行为。旧 `/etc/cm2012-proxy/node-hosts.json` 已移出运行路径，原文件保留在安装备份中。

DNSPod 官方已建议逐步迁移到域名接入；其公告说明上述 IP 入口暂不下线。本轮只确认这些入口在现场可用并通过证书验证，未承诺服务商未来可用性。后续迁移需要再次验证独立引导和 TLS，不能直接恢复到不受保护的节点明文解析。参见[官方公告](https://docs.dnspod.cn/notices/mian-fei-ban-dot-dohbu-zai-gong-kai-ipjie-ru-de-gong-gao/)。

## 安装与验收

新增回归先确认旧实现不能使用动态节点 DNS，再验证显式解析覆盖过期 pins、保持节点身份和普通 DNS，以及非法上游拒绝。Python 3.12.14 公共回归运行 135 项，成功、2 项平台限定测试跳过；真实 ucode、Mihomo 候选检查和独立代码审查通过。

安装两个代码文件及私有节点 DNS 配置后，常规应用流程尝试重新获取订阅规则集合，发生下载失败并恢复旧配置。该下载故障未在本轮修复。最终使用已保存、已校验的规则，仅更新 DNS/hosts；启动前备份，校验其余配置逐项相同，沿用原生健康、防火墙及精确策略路由逻辑，并加本次 revision 限定的 120 秒自动停用保护。节点、DNS 和 LAN 路由验证成功后解除保护。没有把旧规则重新标记为本轮下载成功。

最终状态为 revision 22、active，无 pending/updating/apply_error/update_error，TUN 和接管路由正常。生产核心实测 11/11 节点成功，HTTPS 延迟约 277–1895 ms。ChatGPT 主站、API、认证、静态资源和验证域名的 A 查询均成功，约 78–99 ms；百度查询成功，约 343 ms。随后用户在连接 CM201-2 的终端重新打开浏览器，确认“浏览器已恢复”。

没有调整电脑浏览器设置，也没有读取浏览历史、Cookie 或账户信息。没有实机重启或长期稳定性验收，不将本次启动成功表述为重启验收。
