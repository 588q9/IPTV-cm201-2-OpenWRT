# 恢复条件与当前限制

## 已验证与待验证

功能修复版最终产物已完成两次逐字节一致的离线构建、全部 NAND 只读的 RAM 验收及同一产物的 userdata 重建。实际内部 UBI/UBIFS 启动与重启持久化通过，保留的 mtd0–7 完整摘要不变。网口、WPA2 STA/AP 并发、手机热点转发、LuCI 租约和管理登录均有实测，用户最后确认内部系统验收通过；详情见 [验收记录](验收记录.md)。USB 磁盘读写未验证，标准自动挂载、完整 IPv6 路由与通用升级不列为支持能力。

目前适配固定原厂引导器与内核版本的 Hi3798MV300、1GiB LPDDR3 和 MT7668。物理 NAND 容量动态计算，但页大小、擦除块、OOB、ECC、DDR 参数、模块及启动代码仍须满足校验。仅改容量字段不能让其他硬件获得兼容支持。

## NAND 与内部存储

前 48MiB 固定布局保存引导、boot 和必要硬件参数；最后 userdata 占用所有剩余容量，内部建立 UBI/UBIFS 根系统。原 boot2 和 recovery 分区被回收，OpenWrt 内部启动不要求保留原厂备用 Android 镜像。完整系统和配置在内部闪存中，正式启动不依赖外部盘。

userdata 的物理分区长度大于文件系统可用容量。坏块、UBI 元数据和保留擦除块由 UBI 在分区内部管理，不能把物理容量、UBI 逻辑容量与 `df` 输出混为一谈。核心区存在坏块、参数异常或读回校验失败时，应停止安装或修复操作。

## 恢复资源

保留使用者自己的原厂 fastboot、完整原 boot、迁移前分区表、MLC 校验表、有效 baseparam、misc、swdevinfo、匹配模块与固件。它们的用途是保持硬件初始化、构建匹配系统并支持分析恢复；八个构建输入并不构成完整 Android 备份。

完整 Android 恢复还可能需要原始分区数据、OOB/坏块处理信息以及相匹配的完整恢复工具。曾经使用的原厂 system 文件归档、部分 NAND 备份或电视 update 包都不能直接证明能够恢复完整原厂系统。本项目没有提供完整原厂 NAND 镜像，也不承诺凭这些局部资料恢复 Android。

原厂资料和新产物至少保留在电脑及独立备份位置，记录字节长度和 SHA256。不得把包含设备身份、管理配置或原厂授权信息的备份公开上传。

## RAM 维护与内部启动失败

串口是主要维护路径。引导过程只使用经过校验的本机原厂头、辅助代码与 DDR 参数，BootROM 传输的是 RAM 副本。针对 RAM 的控制台修改或读取钩子不得写入 fastboot 分区。公开 `ram-test` 与 bootstrap 自动入口已实测，均读回全部 NAND 只读参数后才执行内核。失败时先保留日志和当前状态，不盲目反复加载旧调试镜像。

bootstrap 用于给原厂系统建立第一次 RAM APK 构建环境，本身没有完整热点配置。它和完整 `ram-test` 都不会在命令返回后自动恢复内部系统；可用 `py -3.12 tools/project.py restore` 经串口同步并重启，再核对原内部启动状态。当前恢复命令自动检测的是 OpenWrt 控制台；原内部系统为 Android 时需人工核对其启动结果。完整步骤见构建说明，不能把进入 bootstrap 控制台视为完整 OpenWrt 热点已验收。

早期公开产物曾因 sysntpd 的 ujail 在 initramfs 根执行 pivot_root 返回 EINVAL 而重复启动。功能修复版针对固定原厂内核绕过 dnsmasq/NTP 的 jail；最终 RAM 和内部系统均已实际验证 NTP 同步、SSH 交互 PTY 与 HTTPS，内部重启后关键服务各一实例。旧内核仍输出 devpts 选项日志，但实际 /dev/pts 挂载及 PTY 可用。具体结果见验收文档。

内部最小入口检查 userdata 对应的 UBI、`rootfs` 卷、`/sbin/init` 和项目完成标识，初次只读挂载，成功后才进入完整根系统。找不到卷、标识错误或切根失败会进入串口维护环境，不自动格式化或擦除。静态切根程序保留原 RAM 维护根用于失败回退；原安装的实际失败注入测试已经验证，该结论仍需在重新构建的程序与镜像上复核。

恢复正式写入必须使用与当前物理布局一致的产物和新校验清单，按目标边界与读回摘要检查。旧原厂布局探针和旧物理偏移在迁移后不能直接使用。构建和只读 RAM 测试不执行 NAND 写入。功能修复版增加显式 `install --erase-internal-root`，仅重建 userdata；持久分区表和保留 boot 不兼容时拒绝执行。适用条件和操作见 [功能修复与重装](功能修复与重装.md)。

## 无线与管理界面

MT7668 的 hostapd/supplicant 由项目 procd 服务统一管理，默认 wpad 停用。网络、DHCP/DNS 和防火墙接入 UCI/netifd；无线使用专用 cm2012 UCI 配置及 LuCI 页面，不使用标准 mac80211 无线页面。

最终 RAM 已验证 WPA2 STA/AP 并发、热点跟随上游信道、无线 DHCP/路由/DNS/公网访问、手动有线/无线切换、错误密码自动回滚；内部系统再次验证无线连接及返回有线。用户关闭测试手机移动数据后确认最终 RAM 和内部系统的热点管理页面及普通网站可用，也确认上游断开期间热点管理仍可访问。通过项目专用页面配置，并在 90 秒内确认管理可访问。完整验收状态见 [功能修复与重装](功能修复与重装.md)，不要用标准 mac80211 教程替换原厂驱动服务。

热点名称和两个密码由使用者在 `configure` 中指定，公开文件没有统一管理口令。镜像不复制已有设备私钥、证书和随机种子；本次内部安装首次启动生成新的 SSH 主机密钥和 HTTPS 密钥/证书，已通过重启摘要持久化检查。临时验收公钥已移除。

## 升级方式

普通 OpenWrt `sysupgrade` 尚未适配该原厂内核和自定义布局，不能直接刷入通用 armsr 镜像或通用固件包。新增包也须检查 ARMv7 ABI、旧内核接口与原厂驱动兼容性。构建中使用官方 ARMv7 用户空间，不代表官方通用内核或内核模块适用于这个盒子。

官方根系统携带的 APK 数据库仍可能显示 6.12 的 `kernel` 和 `kmod-*` 包；通用模块文件已经从新根系统去除，实际硬件驱动来自原厂 3.18。APK 数据库不是正在运行的内核能力清单，也没有为本机提供可直接使用的内核升级路线。目前不要进行整体 `apk upgrade`，或把数据库中已有的 kmod 记录当作可以加载的驱动。

## 公开仓库边界

代码、模板、锁定清单、纯测试和中文文档可以提交。原厂输入、私人配置、下载缓存、生成镜像、设备密钥、串口日志和历史调试内容通过白名单忽略并保留本机。上传前检查实际暂存文件，Git 忽略规则不负责清理已经提交过的秘密。

GitHub 仓库由使用者自行创建并上传。本项目当前任务不会设置远程地址、自动推送或公开镜像文件。
