# Windows 与盒子串口构建说明

## 状态与范围

本文描述已实现入口和已确认的构建设计。公开流程的首次完整构建、断网重复构建及新产物 RAM 验收仍在进行，本文中的命令不能代替成功的验收记录。历史实机系统已验证内置启动和 AP，但它的私人根系统归档不是公开构建输入。

目前限定已验证的 Hi3798MV300、1GiB LPDDR3、`3.18.24_hi3798mv2x` 原厂内核及 MT7668。引导器和内核必须属于代码中允许的原厂版本；检查失败时停止，不通过修改摘要白名单强行运行。设备容量采用物理 NAND 几何与原厂分区表共同确认，不能以 `df` 的文件系统容量代替。

## 准备环境

- Windows x64 电脑，安装 CPython 3.12 x64。下面示例使用 Windows Python Launcher 的 `py -3.12`；若没有该启动器，替换为自己的 Python 3.12 解释器。当前 Zig 和 PyCryptodomex 发行包均锁定 x64 平台。
- 盒子串口已经接通。当前入口默认 `COM3`，可在 `configure --port` 指定实际端口；控制台为 115200、8N1，关闭 DTR/RTS，传输阶段由程序切换速率。一次只允许一个程序占用串口。
- 本机原厂资料，格式见下一节。盒子须能运行匹配内核下的 ARMv7 `apk-tools 3.0.5`；现有 OpenWrt 可以充当构建工作机。原厂 Android 使用者需要先进入项目独立 RAM 构建环境；自动 bootstrap 已在当前内部 OpenWrt 起点实测，原厂 Android 控制台起点仍须核对。
- `prepare` 阶段能够联网，并有空间保存 Zig、源码、官方根系统和 APK 缓存。`build` 在盒子 RAM 中工作，预检查需要的展开空间和额外余量；空间不足会停止。

不要把通用 ARM OpenWrt 内核模块装给原厂 3.18 内核。项目只使用从匹配原厂系统导出的模块与固件。

## 原厂输入清单

八个文件位于同一个使用者自备目录；文件名是构建接口，数字后缀不代表其他设备上必须使用相同 MTD 编号。

| 文件名 | 内容 | 当前已验证版本的读取范围 |
| --- | --- | --- |
| `mtd0-data.bin` | 完整原厂 fastboot，包含原厂引导和 DDR 参数 | 按 `fastboot` 分区名称读取完整 2MiB 数据区。 |
| `mtd1-data.bin` | 原厂分区表及副本所在分区 | 按 `partition` 分区名称读取完整 8MiB；必须是迁移前原表。 |
| `mtd14-data.bin` | 完整原厂 Android boot 镜像 | 按原厂 `boot` 分区名称读取完整 40MiB；不是当前 OpenWrt 的 12MiB boot。 |
| `baseparam-valid.bin` | 从有效原厂 baseparam 或 baseparam2 提取的参数记录 | 按原厂校验表给出的有效长度与校验值选择。已验证版本为 5804 字节，不包含分区尾部填充。 |
| `mlcverify-head.bin` | 原厂 MLC 启动校验表 | 从原厂 `mlcverify` 起点只读导出至少 64KiB，保留表头与记录。 |
| `stock-support.tar.gz` | 原厂内核模块和无线固件文件归档 | 归档内保留 `system/lib/modules/` 和 `system/etc/firmware/` 相对路径。 |
| `original-misc-data.bin.gz` | 完整原厂 misc 数据的 gzip 归档 | 按原厂 `misc` 分区名称读取 8MiB；构建迁移其前 2MiB 到固定新布局。 |
| `original-swdevinfo-data.bin.gz` | 完整原厂 swdevinfo 数据的 gzip 归档 | 按原厂 `swdevinfo` 分区名称读取完整 16MiB。 |

这些资料可能包含设备身份或原厂授权信息，保留在私人备份中。仓库不提供原厂包；电视 `update.zip` 也不能直接替代这八项输入。

### 只读导出原则

导出应在改变原厂布局前完成。已迁移的盒子只能复用迁移前的可靠备份，不能按当前 `/dev/mtd14` 或旧物理偏移重新读取“原厂 boot”。容量、分区名称及长度与表中情况不符时，先完成兼容性分析。

1. 通过串口读取 `cat /proc/mtd`、`dmesg` 中的 NAND 几何信息，以及 `/sys/class/mtd/mtd*/name`、`size`、`erasesize`。按名称映射 MTD 编号，记录映射和当前启动环境。确认是否暴露整颗 NAND 或各子分区，不能把两者相加计算容量。
2. 只打开 NAND 作为输入，目标文件写到 `/tmp` 的 RAM 文件系统、电脑或外部备份盘。确认 `/tmp` 为 tmpfs，并检查空闲空间。读取报错、长度不足或校验不一致即停止；不执行 `flash_erase`、`nandwrite`、`ubiformat` 或向 `/dev/mtd*` 写入的命令。
3. 按名称逐一读取完整 fastboot、partition、原 boot、misc、swdevinfo。先核对输出字节数，再生成 SHA256；转移到电脑后再次核对。misc 与 swdevinfo 使用 gzip 归档，解压后的长度仍须正确。NAND 数据区读取不包含 OOB，不能把这些文件声称为完整原始 NAND 备份。
4. 导出 MLC 表头，校验标识、记录数量、记录范围和表 CRC。分别读取 baseparam 与 baseparam2，依据对应记录的偏移、有效长度和 CRC 选择有效参数。不要把全分区填充文件直接改名为 `baseparam-valid.bin`；若两个副本都无效则停止。当前流程仍需要使用者提供已验证的有效记录，没有一键原厂导出子命令。
5. 在只读挂载的原厂 system 中归档模块和固件，保留 Linux 文件权限及符号链接。若当前 system 无法只读读取，应使用自己的可靠文件备份，不能从普通 OpenWrt 包补出原厂驱动。
6. 将八个输入文件与几何记录、长度和 SHA256 保存在电脑，并另存一份外部备份。构建档案固定它们的摘要，后续输入变化会使校验失败。

例如，已确认 `fastboot` 确实为 2MiB 且 `/tmp` 为 tmpfs 后，可按名称读取；这段命令只读取 MTD，写入 RAM。务必在原厂布局下先核对其余分区，不能按例子推断整颗 NAND 的范围。

```sh
mtd_fastboot=
for entry in /sys/class/mtd/mtd*; do
    [ -r "$entry/name" ] || continue
    [ "$(cat "$entry/name")" = fastboot ] || continue
    [ "$(cat "$entry/size")" = 2097152 ] || exit 1
    mtd_fastboot=/dev/${entry##*/}
done
[ -n "$mtd_fastboot" ] || exit 1
[ ! -e /tmp/mtd0-data.bin ] || exit 1
dd if="$mtd_fastboot" of=/tmp/mtd0-data.bin bs=8192 count=256 || exit 1
[ "$(wc -c </tmp/mtd0-data.bin)" = 2097152 ] || exit 1
sha256sum /tmp/mtd0-data.bin
```

其余数据按已核对的名称和长度同样只读导出；若环境只有整颗 NAND 的只读映射，需从已校验原厂表计算范围，不能照搬旧调试日志的固定偏移。完整资源导出工具尚未提供，串口原始二进制不能直接复制粘贴为文件，应使用有长度和摘要校验的传输工具或外部备份介质。

若原厂 `/system` 已确认只读挂载，且 RAM 空间足够，可保留模块和固件路径生成支持归档：

```sh
tar -czf /tmp/stock-support.tar.gz -C / system/lib/modules system/etc/firmware
gzip -t /tmp/stock-support.tar.gz
sha256sum /tmp/stock-support.tar.gz
```

备份介质只用于导出和恢复，不是正式 OpenWrt 的运行依赖。

## 统一命令

在项目根目录执行。以下是当前入口接受的命令，完整执行效果以本轮验收为准。

```powershell
py -3.12 --version
py -3.12 tools/project.py prepare
py -3.12 tools/project.py configure --stock-dir .\local\stock-original --port COM3
py -3.12 tools/project.py check
py -3.12 tools/project.py check --device
py -3.12 tools/project.py build --output .\output\current
py -3.12 tools/project.py verify --output .\output\current
```

`prepare` 按锁定版本下载并校验资源，也可用 `--import-dir` 从自己的已有缓存导入摘要相符的文件。服务器资源缺失或摘要变化时停止，不自动寻找更新版本。不要随意修改资源锁使下载通过。

官方 APK 发布目录可能替换文件，即使包版本字符串不变，摘要也可能变化。请保存完整的锁定缓存，便于长期离线复现。本轮资源锁于 2026-10-11 核对：hostapd 三包为 r5，wifi-scripts 使用当前签名索引对应的新内容。21 个 URL 当日均有成功响应；这不保证日后仍可下载。更新锁必须重新核对签名、依赖、重复构建和实际无线功能，不能自动回退到不同版本。

依赖文件保存于 `local/cache/`，APK 与签名索引保存在 `local/cache/apk/`。Python wheel 激活到 `local/python-deps/`，不要求将这些依赖安装进全局 Python。`requirements.lock` 固定六项必要依赖：pySerial、pyserial-asyncio、ymodem、ordered-set、Passlib 和 PyCryptodomex；实际 URL、字节长度与摘要以 `resources.lock.json` 为准。PyCryptodomex 使用支持 CPython 3.12 的 Windows x64 稳定 ABI wheel，为 hiloot 顶层导入的芯片属性模块提供 AES 接口；没有加入可选终端美化包或反汇编工具。

`configure` 交互输入自己选择的热点名称、热点密码和 root 管理密码，原厂文件路径和密码配置保存到被忽略的 `local/config.json`。相同管理密码会复用已有摘要，避免重复构建因随机盐而变化。本地配置、缓存和生成镜像应按私人文件保管。

`check --device` 只读复核运行内核、物理 NAND 几何、MTD 总长度与 APK 工具版本。原厂 Android 没有相应 APK 工具时不能直接执行完整 `build`，应先启动独立 RAM 构建环境。入口为 `ram-test --bootstrap`；具体实测起点与结果见验收记录，不应在缺少可靠恢复资料时直接尝试。

### 首次从原厂系统建立 RAM 构建工作机

现有内部 OpenWrt 可以直接提供原生 APK 工具。仍在原厂 Android 的使用者，应先在原厂布局下完成八项只读备份并运行 `prepare`、`configure`、不带 `--device` 的 `check`；这些步骤不要求盒子已经有 APK 工具，也不要求已有 `rootfs.tar.gz`。`configure` 依据本机原厂资料建立档案，尚不等于核对了当前实机 NAND 几何。

然后保持匹配原厂内核的 Linux 串口控制台可用，执行以下顺序。bootstrap 使用锁定官方根系统、原厂内核与模块、重新编译的兼容 ubusd，在 RAM 中建立最初的 APK 工作环境；之后再由这个工作环境组装完整系统，避免依赖历史私人根系统归档。

```powershell
py -3.12 tools/project.py ram-test --bootstrap --output .\output\bootstrap
py -3.12 tools/project.py check --device
py -3.12 tools/project.py build --output .\output\current
py -3.12 tools/project.py verify --output .\output\current
```

bootstrap 需要同步并重启当前系统，再通过 BootROM 加载原厂引导器的 RAM 副本；串口必须保持连接，不能让其他软件同时打开端口。该环境预期首先提供串口控制台和 ARMv7 APK 工具，没有加入完整热点配置与新增无线 APK，因此不能以搜索不到测试热点作为 bootstrap 失败的判据。出现控制台后应确认内核、NAND 只读标志和 APK 版本，再执行 `check --device`；完整自动启动路径仍以实机验收记录为准。

`build` 在 Windows 编译辅助程序，然后通过串口传输到盒子的独立 `/tmp/cm2012-build-*` 目录。盒子 APK 使用独立根目录、本地签名仓库、禁网络和禁安装脚本的选项，显式补齐必要账户与启动链接。构建前后检查活动包数据库、配置摘要和相关服务 PID；错误诊断留在该作业目录，不能手动删除正在使用的根目录。

源码通过 Zig 编译；用于链接的 ELF 节表恢复副本只存在本机工作目录，不替换系统运行库。新根系统移除通用 6.12 内核模块，加入原厂 3.18 模块、固件、兼容 ubusd、自定义 AP 服务和独立网络配置。

当前保留官方根系统的 APK 安装数据库，其中可能仍列出官方 `kernel` 与 `kmod-*` 软件包；构建已经移除它们对应的通用模块文件。这些数据库条目不表示原厂 3.18 内核具备相应功能，也不能用来判断驱动兼容性。不要根据 APK 的“已安装”状态启用通用内核模块、执行整体包升级或刷入通用 armsr 固件。

## 产物与分区

默认输出目录为 `output/current/`，包括：

- `rootfs.tar.gz`：规范化的完整用户空间归档。
- `boot.img`、`internal.cpio.gz`：内部启动镜像和最小维护根。
- `ram.cpio.gz`：完整 RAM 验证系统；`ram-test` 从已校验的原厂 boot 提取 `kernel.uImage`，通过受控串口入口装载两者。
- `ptable.bin`、`mlcverify.bin`：本次布局和启动校验资料。
- `baseparam.bin`、`baseparam2.bin`、`misc.bin.gz`、`swdevinfo.bin.gz`：本机硬件参数迁移资料。
- `install-resources.tar.gz`：本次清单对应的安装资料、阶段脚本和维护工具。构建与 RAM 测试不会执行其中的 NAND 写入阶段。
- `manifest.json`：本次产物长度、SHA256、几何和分区边界。

这些产物含本地配置和原厂数据，不进入公共 Git 提交。安装保护必须使用本次生成清单，不能沿用历史镜像摘要。

| 分区 | 起点 MiB | 固定大小 MiB |
| --- | ---: | ---: |
| fastboot | 0 | 2 |
| partition | 2 | 8 |
| misc | 10 | 2 |
| mlcverify | 12 | 4 |
| swdevinfo | 16 | 16 |
| baseparam | 32 | 2 |
| baseparam2 | 34 | 2 |
| boot | 36 | 12 |
| userdata | 48 | 物理 NAND 总容量减 48MiB |

容量采用 64 位字节值并按擦除块对齐，拒绝空洞、重叠或越界。不同容量只改变最后 userdata 的长度；坏块及 UBI 管理开销不从分区末尾手动扣除。

## 验收要求

纯测试在没有私人备份、工具缓存或盒子的公开克隆中运行。需要原厂资源或设备的集成验证应明确声明前提，缺失输入不能被当作通过。

联网 `prepare` 完成后，分别构建到两个输出目录并运行 `verify`。`build` 的 Python 进程拒绝网络连接，盒子 APK 明确使用 `--no-network`；验收记录应区分这两项控制与电脑物理断网。输入资源、源码、原厂资料及 `local/config.json` 相同的情况下，比较两份 `manifest.json` 的所有产物摘要。再次运行 `configure` 更换密码或原厂输入会改变产物，不能作为同输入复现比较。

完整 RAM 验收通过 `ram-test --output` 装载新生成的 `ram.cpio.gz` 与原厂内核。程序设置全部 NAND 分区只读的启动参数，读回 `bootargs` 并逐字核对成功后才执行 `bootm`。进入系统后仍应检查各 MTD 的只读标志，再检查 procd、ubus、AP、手机 DHCP 和 LuCI 登录。不能直接套用 Android 启动镜像入口来证明 NAND 只读。完成测试后可恢复内部系统，或按 [功能修复与重装](功能修复与重装.md) 显式重建 userdata。普通构建和 RAM 测试不会正式写入新产物。

`ram-test` 返回电脑命令行后，盒子仍停留在 RAM 系统。验收完成后运行以下命令，经串口同步并重启，由未修改的原厂引导器重新加载原内部系统：

```powershell
py -3.12 tools/project.py restore
```

`restore` 使用本地配置指定的串口，继续要求锁定缓存和原厂输入校验通过。它等待内部 OpenWrt 串口控制台；这适用于已经内部安装 OpenWrt 的工作机。仍保留原厂 Android 的盒子重启后应回到原厂系统，当前自动检测的 OpenWrt 提示符不适用于 Android，需自行核对原厂串口启动状态。恢复后应重新验证原配置和服务，不能仅凭发送重启命令或检测到提示符就记录完整恢复成功。

## 版本控制与本机文件清理

未追踪不等于可删除。新增的 `configs/templates/` 无线服务、LuCI 页面和 RPC、`tools/cm2012/` 兼容工具及补丁、`tests/` 回归测试、中文文档与第三方许可证都属于正式源码，应纳入提交。测试脚本和测试数据是可重复验证所需的输入，不能当作运行测试产生的文件忽略。

`.gitignore` 使用公开文件白名单，并在白名单目录内排除 Python 字节码、pytest/mypy/ruff 缓存和 Zig 编译缓存。`local/`、`output/`、`backup/`、`downloads/`、历史分析资料、IDE 状态及日志已被忽略。忽略只决定是否进入版本控制，不代表这些文件都没有用途。

| 本机文件 | 保留与清理原则 |
| --- | --- |
| `local/config.json`、原厂输入和 `backup/` | 私人配置及恢复资料，保留，不公开 |
| `local/cache/`、`local/python-deps/`、`local/toolchain/` | 离线构建资源与依赖，保留；删除后可能需要重新准备 |
| 当前 `local/build/` 和 `local/zig-*-cache/` | 当前构建的源码展开、工具和增量缓存，可重新生成；保留可减少编译时间 |
| 最终镜像及匹配的验收记录 | 保留用于验证和维护；包含私人输入，不公开 |
| 临时测试导出/克隆、已被最终版替代的候选镜像、重复传输包、旧编译缓存与字节码 | 确认用途及依赖后删除，不需要保留所有中间副本 |
| 实机验收日志和摘要记录 | 保留在忽略目录，作为问题分析及实测证据；不能当作普通临时文件批量删除 |

清理前核对每个目标的绝对路径仍在项目内，排除正式源码、Git 元数据和目录链接，不使用覆盖整个工作区的批量清理命令。本次清理保留最终 C/D 镜像、bootstrap-final、离线资源与验收日志；临时克隆目录删除后，其已完成验证的日志和摘要记录仍保留。
