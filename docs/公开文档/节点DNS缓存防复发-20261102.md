# 节点 DNS 缓存防复发（2026-11-02）

## 现场恢复与本次源码的区别

此前排查观察到节点入口地址变化，常驻 Mihomo 仍命中旧地址；主 DNS 使用的节点同时失效，使普通网页解析超时。重新解析后，11/11 节点连续两轮通过，并观察到 LAN 代理转发。那次没有修改生产配置或源码，没有重启，也没有安装防复发机制。私人排查资料保留在本机，不进入源码包。

本次新增代码仍需单独设备验收，不能用上述现场恢复结果证明新机制已实测通过。

## 实现与功能归属

- `cm2012-proxy-lib.uc` 只生成策略：CM2012-DNS 改为 fallback，60 秒健康检查、3 秒超时，保持可用的首选节点，首选失效后切换。普通业务组和 CM2012-DEFAULT 的选择语义保持；空 DNS 节点集合使用 REJECT，避免转成直连。所有节点同时不可用仍可能导致 DNS 失败。
- `cm2012-proxy-service.uc` 负责恢复状态：已启用、本地核心和接管路由就绪，且没有设置事务、订阅更新或恢复时，最多每60秒检查一次。连续两次失败才刷新 DNS 缓存并重测；两次刷新尝试至少间隔300秒，尝试时间先保存再执行接口。
- `cm2012-proxy-native.uc` 检查 DNS 组的代理连接，再用本机1053查询公开 example.com 的 A 记录；固定合成健康域名不能代替这一检查。
- `proxy_api.h` 提供有超时和响应上限的固定回环接口，只访问127.0.0.1:9090，从私有文件读取认证，令牌不进入命令参数、输出或日志。缓存刷新不需要初始化 curl/TLS，也不重启 Mihomo。
- LuCI 分别显示本地核心是否就绪，以及公网代理和 DNS 的最近检查结果。尚未检查、配置已变、停用、事务繁忙或证据超过180秒时显示尚未验证。

公网检查失败保留接管和现有配置，只进行上述有限恢复；不会因为公网探测失败自动改成直连或重启核心。原有本地核心/TUN/API/DNS失效保护保持原来的恢复直连策略。

## 探测数据与隐私

节点专用加密 DNS、节点域名/SNI 和 TLS 校验保持。健康检查使用既有 Cloudflare 提供方的固定 `https://1.1.1.1/cdn-cgi/trace`，通过代理发起 HEAD，避免该探测再依赖故障的普通域名解析；DNS 检查只查询公开 example.com。提供方会收到这些合成探测请求，主机上不保存响应正文、节点地址或真实业务域名。状态只提供结果枚举、时间、计数和固定错误类别，原有凭据和 RPC 权限边界保持。

这是一项有界的故障发现与恢复机制，不保证上联、所有节点或公共 DNS 服务故障时仍可访问网络。固定站点被阻断也会造成失败提示；此时不会因此撤销代理接管。管理 HTTPS 策略仍按原要求暂缓。

## 验证范围

公开回归使用生产策略/状态机和模拟时间/系统边界，覆盖切换配置、两次失败、刷新成功或失败、重试、冷却、事务跳过、过期状态和隐私输出。原生接口通过本地假服务器验证固定请求、认证、响应边界和错误处理；POSIX 原生测试在 Ubuntu 运行，Windows 明确跳过。另运行锁定 ARM 交叉编译与完整公共回归。

新机制没有连接现场设备，也没有完成真实节点切换、长时间观察或重启验收。相关接口以固定版本为准：[Mihomo 缓存路由](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/hub/route/cache.go)、[fallback](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/adapter/outboundgroup/fallback.go)、[URLTest](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/adapter/adapter.go)。
