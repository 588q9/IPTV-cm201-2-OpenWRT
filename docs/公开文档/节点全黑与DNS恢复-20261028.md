# 节点全黑与 DNS 恢复（2026-10-28）

后续：本方案的静态节点地址在 10 月 29 日已过期，现已替换为动态加密节点 DNS；当前状态与安装说明见[动态节点 DNS 与浏览器恢复](动态节点DNS与浏览器恢复-20261029.md)。下文保留当日历史记录。

用户报告启用自动分流后 MetaCubeXD 中所有节点均不可用，且下游无法访问互联网。排查开始时设备已停用代理，revision 19，无接管路由或待确认事务。

## 原因与对照

最新订阅与保存的 11 个 Hysteria2 节点参数一致。隔离核心只监听回环，关闭 TUN，不接管 LAN，仍复现 11 个节点全部失败。节点域名经当前上联明文 DNS 返回大量交叠地址；AliDNS 的加密解析亦未返回可用入口，仅换用 AliDNS 不能恢复连接。

用户分别明确授权 AliDNS 对照，以及向 Cloudflare 查询同样三个节点域名并在验证成功后应用。通过本机证书验证的 Cloudflare DoH 获取节点解析，仅将这些映射加入隔离配置，即有 7/11 节点通过 HTTPS 延迟测试，百度、Cloudflare、example.com DNS 查询恢复。此单变量对照确认错误节点解析是本轮整体断网的原因。

盒子直连 `cloudflare-dns.com` 的 TLS 握手失败，另测 Cloudflare 备用域名及两个公开 IPv4 DoH 入口超时，因此未把不可直连的 Cloudflare 设置成无代理的节点解析器。Cloudflare 的服务与接口可参考[官方入口说明](https://developers.cloudflare.com/1.1.1.1/infrastructure/network-operators/)。

## 本次修复

设备私有文件 `/etc/cm2012-proxy/node-hosts.json` 保存三个经验证的节点映射，权限 0600。运行时将它传入配置编译器；编译器仅保留当前静态或 provider 节点主机对应的映射，校验地址格式、数量及本地/私网/组播/基准测试网段，去除重复地址。普通域名、无关映射及订阅携带的 hosts 不会因此被放行。

保留节点原始 server、SNI、认证与证书校验，不改变系统 DNS，不关闭 TLS 校验。映射在再次启用、订阅重编译及启动时的配置重建中继续生效；无需重新构建或刷写固件。

这是经验证的本地节点地址映射，**不是自动更新的 DNS 缓存**。入口地址变化或订阅新增节点域名时需要重新获取、验证并刷新映射。本次没有安装自动外发节点域名的定时任务，也没有将私有映射写入源码或公共文档。

## 验证结果

- 新增编译器回归先在旧实现失败，再验证映射生效、无关域名隔离、非法地址拒绝、节点 TLS 身份保留和 provider 节点支持。
- 使用锁定系列 Python 3.12.14 运行公共回归：135 项，成功，2 项平台限定用例跳过。默认 PATH 的 Python 3.7.4 首次运行出现版本不兼容错误；改用既有 3.12 环境后全部通过，未为旧解释器改项目代码。
- 真实设备 ucode 编译与 Mihomo 配置检查通过，两个源文件安装前基线一致、安装后三个文件摘要一致。
- 通过设备自带确认事务启用并确认，最终 revision 20、active，无 pending/updating，TUN 和 LAN 路由正常，守卫失败计数为 0。
- 11 个节点中 7 个实测成功，HTTPS 延迟约 398–1385 ms；其余 4 个共享另一入口，仍握手超时，未声称全部节点可用，也未确定这四个节点超时的最终原因。
- 实际主 DNS 已选中本轮可用节点，三个公共域名查询均成功，约 173–175 ms；默认业务策略也落到可用节点。
- 后续只读快照有 86 条 TUN 连接，其中可观察到使用代理节点的连接；15 秒内总上传增加 154,469 字节、总下载增加 362,160 字节。此证据确认实际转发发生，不代表全部应用或长期稳定性验收。
- 用户随后使用连接 CM201-2 的终端实测，明确确认“已经恢复”上网。

本轮没有重启设备；重启后映射读取路径经过原生编译检查，但未将其表述为实机重启验收。
