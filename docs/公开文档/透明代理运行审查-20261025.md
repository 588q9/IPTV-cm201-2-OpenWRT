## 优先处理的问题

### 1. P1：urngd 明显耗 CPU，熵池仍很低（实机确认）

短时全进程采样中，系统四核总 CPU 忙碌约 56.6%，`urngd` 占总算力约 49.9%，Mihomo 约 3.4%。后续两段 5 秒采样中，`urngd` 仍约占总算力一半，接近占满两个核心；熵计数为 10、5、3 bit。进程有两个运行线程，版本为 `2025.10.03~f17e33d9-r1`。

此外有约 10 个原厂多媒体、USB 等内核线程处于 D 状态，会抬高 load average；因此不能把 load≈12 解释为 Mihomo 独自过载。CPU 占用必须按计数差分判断。

影响是持续消耗处理余量和电力，并且本次未观察到熵池被有效补足。高 CPU 与低熵同时存在已经证实，但具体是 jitterentropy 时钟适配、采集健康检查还是厂商随机数实现问题，尚未定位到函数级根因。先做隔离取熵与 CPU 对照，验证修复后熵池增长和 TLS 行为；不宜直接停掉安全熵源作为性能修复。此前订阅下载器的 getrandom 修正不等于整个系统的熵守护已修好。

证据：`local/audits/20261025-active-proxy/cpu-summary.json`、`entropy_cert.txt`、`entropy_recheck.txt`。urngd 的设计职责可对照 [OpenWrt 官方项目说明](https://github.com/openwrt/urngd)。

### 2. P1：回滚失败后决策锁不释放，自动重试被永久阻塞（本机复现）

位置：`configs/remote-proxy/cm2012-proxy-service.uc:165`、`:213`、`:309`。

`rollback()` 建立 `decision.lock` 后，`rollback_internal()` 中的 fw3 reload 等操作一旦失败，异常分支保留事务和锁。之后守卫必须再次 mkdir 同一个锁才会恢复，于是即使故障已经消失，也不能重试；手动回滚和立即停用同样被阻止。

复现：第一次 fw3 reload 返回失败，恢复正常后运行两次 guard，事务和锁仍存在；再次 rollback 返回“事务正在结束”，disable 返回失败。需要人工恢复或重启路径才能解除；本次未在现场制造该故障。

建议保留持久事务并区分“正在处理”与“上次处理失败”，增加可验证的锁归属/失效回收和安全重试；补充回滚操作自身失败的测试。

### 3. P1：订阅更新跨过期限时可能丢掉恢复快照（本机复现）

位置：`configs/remote-proxy/cm2012-proxy-service.uc:295`、`:304`。

触发窗口：候选配置已经发布，阻塞操作跨过更新的 300 秒期限，worker 先于下一次 guard 观察到超时。catch 只有在 `update_alive(token)` 为真时才恢复旧文件，却无条件删除 undo 和 updating；期限已过恰好使恢复分支被跳过。

复现输出显示“现有配置已保留”，实际上旧配置未恢复，新配置仍落盘，undo 和更新记录均已删除，路由未接管。此问题与普通下载失败保留旧配置不同，现有测试先让 guard 取消更新，漏掉 worker 自身先超时的窗口。

建议将“仍拥有本次 token/revision 的恢复权限”和“仍在执行期限内”分开判断；确认恢复成功前保留 undo。两个恢复缺陷的可重跑脚本：`local/audits/20261025-active-proxy/proxy-lifecycle-edge-cases.cjs`。根审查进程已独立重跑，退出 0 并输出 `AUDIT_REPRODUCED_2_LIFECYCLE_DEFECTS`。

### 4. P2：LuCI 与代理面板证书过期（实机确认）

`/etc/uhttpd.crt` 和 `/etc/cm2012-proxy/cert.pem` 均为：

```text
notBefore=Sep  9 01:46:40 2001 GMT
notAfter=Oct 11 01:46:40 2002 GMT
```

设备当前日期已经正确，NTP 进程运行中。证书时间表明其生成时很可能尚未校时，但本次未重新追踪最初生成过程，不能将这一推断当成已确认根因。

影响是 HTTPS 客户端有效期校验失败；加密通道仍可建立，并不等于代理流量整体停止。`cm2012-proxy-native.uc:65` 只在副本缺失时转换原证书，没有有效期检查或续期同步；以后只更新 uhttpd 原证书也不会自动替换已有面板副本。

建议校时后更新设备证书，原子同步面板副本并验证加载结果，再增加到期检测。本次未生成证书或重启 HTTPS/Mihomo。

## DNS 与兼容性改进

### 5. P2：DNS 是独立的手工选点单点，健康检查不能证明外部出口可用

`cm2012-proxy-lib.uc:162` 生成 `CM2012-PROXY type=select`，`:194` 固定主 DNS 经该组访问 Cloudflare DoH。它收集原始节点，没有采用订阅里的自动回退主组。业务组切换不等于 DNS 出口也会切换。[锁定版本 Selector 源码](https://raw.githubusercontent.com/MetaCubeX/mihomo/v1.19.32/adapter/outboundgroup/selector.go)确认：选中项不可匹配时回到第一项，手工 select 不提供按可用性自动故障转移。

现场 11 个节点中有 3 个最近探测均失败，但 DNS 当前选中的节点可用，1053 正常；所以此项是容错缺口，不能用来解释下节的上联 DNS 超时。

另 `cm2012-proxy-native.uc:217` 的 DNS 健康探针命中本地静态 hosts `cm2012-proxy-health.invalid`，配合本地 API/PID/TUN 能确认核心存活，不能验证真实 DoH 或代理节点。建议为 DNS 出口提供明确的自动回退策略，分别展示核心、真实解析和节点连通状态；外网一次探测失败不应直接触发恢复直连。DNS 中指定代理与 bootstrap 的职责见 [Mihomo 官方 DNS 文档](https://wiki.metacubex.one/config/dns/)。

### 6. 上联 DNS 对个别域名超时（实机确认，范围有限）

盒子上联和系统 dnsmasq 均依赖 `192.168.1.1`。重复查询 `example.com A`，上联 53 和本机 dnsmasq 53 超时，而代理 1053 正常。`baidu`、`qq`、`bing`、`github.com`、`cloudflare-dns.com` 上联解析约 8–25 ms，说明不是所有系统 DNS 都失效。

盒子自身发起的查询不经过 LAN PREROUTING 劫持，因此不能把此结果套用到已经接管的下游客户端。对确实受影响的域名，系统服务、直连重解析或使用域名的节点 bootstrap 有潜在风险。尚不能断言是上游过滤、转发故障还是其他解析问题。

建议先验证独立上联解析备用路径，保持节点 bootstrap 与代理 DoH 的依赖关系无环，避免将系统 DNS 整体指向依赖本机代理的出口。证据：`dns.txt`、`internals.txt`、`cpu_processes.txt`。

### 7. P2：provider 内联转换静默丢失过滤与健康检查语义（合成配置复现）

`cm2012-proxy-lib.uc:143` 仅保留 `type:inline` 和 payload，丢弃 provider 的 `filter`、`exclude-filter`、`health-check`、`override`。复现输入只允许 `healthy`，实际生成的 inline 仍包含 `metadata` 和 `healthy` 两节点，原健康检查也不存在。字段语义见 [Mihomo 固定版本 provider parser](https://raw.githubusercontent.com/MetaCubeX/mihomo/v1.19.32/adapter/provider/parser.go)。

当前现场使用 11 个静态节点，本次未发现因此受影响。对未来 provider 型订阅，建议保留明确允许的字段，或在导入时显式拒绝不支持的语义，避免看似导入成功而行为变化。

### 8. P2：组图环检测存在指数复杂度（合成配置复现）

`cm2012-proxy-lib.uc:155` 对共享子图重复 DFS，没有全局已完成集合。构造每组引用前面各组的合法无环图，20 组、约 1.96 kB 输入即可产生约 104 万次递归，本机约 0.6 秒；24 组理论约 1678 万次。256 组上限不能限制这类输入的计算量，在 ARM 上可能让准备 worker 长时间占用 CPU，直至守卫超时取消。

建议使用带访问状态的线性图遍历，并限制总边数。该现象尚未在当前实际订阅中观察到。第 5、7、8 项的本机复现入口：`local/audits/20261025-active-proxy/compiler-boundaries.cjs`，已独立重跑。

### 9. P2：缺少 K 关机链接，enabled 状态误报（源码与实机确认）

`tools/cm2012/proxy.py:36` 只生成 S17/S94/S95 启动链接。Mihomo 的 `STOP=10`、guard 的 `STOP=09` 没有对应 K 链接；现场 `/etc/rc.common` 的 enabled 判断同时检查 START 与 STOP 链接，因此两个服务正在运行，enabled 却返回 1。

应补齐关机链接并纳入安装/撤销清单，使正常关机 stop 钩子和管理状态一致。S 链存在，不能由此推断“重启一定不自启”；本次没有重启验收。

## 观察项与验收边界

- eth0 的累计 TX drop 约 68.5 万，后续两段短时采样未继续增长；尚不能据此归因当前丢包或调整队列。需要带业务流量的差分与链路统计。
- dmesg 的 `mtd8 is already attached` 出现在引导阶段，随后成功挂载 UBIFS；本次没有发现持续 UBIFS I/O 错误或 OOM，不能把该引导消息当成现有 NAND 损坏。
- 固定 MTU 1280、gVisor、关闭 GSO 与旧内核兼容有关，本次没有足够吞吐证据支持直接改大 MTU 或切换栈。
- 当前无公网 IPv6 路由，但未来启用 IPv6 后不能继续沿用“已覆盖全部终端流量”的假设；应用 DoH/DoT 也不在普通 53 劫持覆盖范围。
- 未进行断电/重启、节点全部失效、真实回滚失败、两小时负载或 24 小时稳定性测试。现有真实连接快照证明流量已接管，不证明全部应用规则正确或长期恢复可靠。
- README 的最新简述仍含“代理停用/等待规则验收”的旧状态，与当前启用状态及更详细修复记录不一致，应在下一次交付时同步。

建议修复顺序：熵源 CPU/随机数适配、两个恢复事务缺陷、证书与 DNS 容错，随后处理 provider 语义、图遍历上限及关机链接，并安排有恢复通道的重启与故障演练。当前审查只形成报告和本地证据，未实施上述修复。

本机证据集中在已忽略目录 `local/audits/20261025-active-proxy/`。日志时间为 UTC，换算北京时间需加 8 小时；本次核心采样约为北京时间 16:55–17:06。报告不含私人订阅 URL、节点地址、Token、secret 或密钥。

## 当日后续命名修正

用户指出本地生成的 `CM2012-PROXY` 容易被误解为通用代理入口。已更名并拆分为主 DoH 专用的 `CM2012-DNS` 和按需生成的普通流量兜底组 `CM2012-DEFAULT`；实机只需要前者。更名已同步源码、页面说明及设备，保留当前选点并通过热加载、DNS 与配置摘要验证。此项修正不改变手工选择的故障转移方式，本文其他缺陷仍按原审查结论保留；代码行号对应审查时版本。实施及验证记录见《CM2012 网络扩展实施与启用》的“代理、订阅与确认”段落。
