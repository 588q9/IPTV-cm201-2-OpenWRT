# 高优先级恢复与熵耗修复（2026-10-27）

本次承接透明代理运行审查的三个 P1：回滚失败后锁死、订阅更新超时后丢失恢复快照，以及 urngd 持续占用两个核心但熵计数很低。范围限定于恢复状态机、原生锁/worker 终止边界和本地健康探针。用户授权维护验证临时启用，结束后恢复停用。

## 修复内容

决策互斥改用稳定 inode 的非阻塞文件锁；文件以 close-on-exec 打开，进程退出或被 SIGKILL 时内核释放锁。持久事务只在文件和运行状态均恢复完成后清除。worker 取消同时验证 PID、启动时间、进程组、会话和命令身份；子进程未退出时保留恢复记录，避免旧命令与恢复操作并行改写文件。

更新 token 的归属和执行期限分开判断。超过期限后，仍拥有当前 token/revision 的 worker 可以恢复旧文件；取消和开机恢复依赖持久 undo。旧 revision 不能覆盖后续修改。开机阶段先恢复文件和撤销接管意图，网络就绪后再恢复运行状态。恢复失败保留记录，守卫继续重试。

熵问题的主要触发源是周期性健康检查中的系统 curl。此版本 curl 即使请求本机 HTTP，也会初始化 mbedTLS 随机源。跟踪一个连接本机关闭端口的独立诊断进程，观察到 31 次 `/dev/random` 的 readv，熵计数从 822 降至 169 bit。探针约每五秒运行，持续消耗阻塞随机源，使 urngd 不断补充。

既有下载器增加固定 `health` 动作，直接通过 socket 请求 `http://127.0.0.1:9090/version`。它只读取固定私有 secret 文件，保留 Bearer 鉴权、HTTP 200 检查、完整 Content-Length 检查、4 KiB 总响应限制、两秒进程截止和外层三秒保护；不接收调用者提供的 URL，不使用代理或重定向，也不初始化 TLS 库。PID、TUN 和本地 DNS 检查仍保留。真实 syscall 跟踪该动作的随机设备读取和 getrandom 调用均为零。

订阅 HTTPS 下载仍使用原有证书验证、重定向限制和已就绪内核 CSPRNG 回调。没有停用或替换 `/sbin/urngd`、修改熵阈值、弱化健康检测或将 urandom 输出回灌计熵。锁定的旧 jitterentropy 还存在硬件时钟模式下创建无用计数线程的现象；本次仅保留诊断证据，没有发布该上游修改。

## 实机运行验收

临时启用后保持 active，TUN、策略路由、鉴权 API 和 DNS 均正常；DNS 查询约 120 ms。五分钟差分结果如下，CPU 均按四核总算力计算：

| 指标 | 结果 |
| --- | --- |
| urngd 平均 CPU | 0.965%，此前异常采样约 49.9% |
| 系统总忙碌 | 4.492% |
| 熵计数 | 918–978 bit |
| 十次完整 32 字节 `/dev/random` 读取 | 均成功，最长约 0.57 秒 |
| 停止人工消耗后的补熵 | 约 2.02 秒达到 937 bit，超过 896 bit 目标 |

读取验收使用 `iflag=fullblock`，确认每次读满 32 字节，不能把一次短读取算作通过。临时运行结束后恢复停用，revision 15。随后再次准备临时启用但不确认，正常重启；开机恢复已返回 revision 15 停用直连，无 pending/updating。十分钟重启后观察通过：urngd 占四核总算力约 0.245%，系统总忙碌约 0.933%，熵计数 917–1030 bit。守卫及控制面正常，三个安装文件摘要一致，未观察到 OOM、崩溃或 UBIFS 错误。最终保持 revision 15、停用直连，无 pending/updating、TUN 或接管路由。
